# 게시판 API 기능명세

기본 주소는 `http://localhost:8080`입니다. 실행 방법은 [README](../README.md), 실행 가능한 명세는 `/swagger-ui.html`, OpenAPI JSON은 `/v3/api-docs`에서 제공합니다. 기본 웹 화면 6개인 게시글 목록(`/`), 상세(`/post.html?id=게시글ID`), 작성(`/write.html`), 수정(`/edit.html?id=게시글ID`), 로그인(`/login.html`), 회원가입(`/signup.html`)을 구현했습니다. Docker Compose의 앱·DB 포트는 로컬 과제용으로 호스트의 `127.0.0.1`에만 바인딩합니다.

## 상태 확인 (Actuator)

게시판 API와 별도로 `GET /actuator/health`를 로그인 없이 제공합니다. 정상 상태에서는 HTTP `200`과 다음 JSON을 반환합니다.

```json
{"status":"UP"}
```

`DOWN` 또는 `OUT_OF_SERVICE`는 HTTP `503`과 해당 `status`를 반환합니다. 이 응답은 게시판 오류의 `{"message":"..."}` 형식과 다릅니다. `HEAD /actuator/health`는 같은 상태 코드와 본문 없는 응답을 제공합니다.

DB 연결과 작업 디렉터리 디스크 상태를 종합하지만 세부 정보·구성 요소는 표시하지 않습니다. 다른 Actuator 엔드포인트, `/actuator` 목록과 `/actuator/health/db` 같은 하위 경로는 사용할 수 없습니다. 차단 경로는 비회원 `401`, 로그인 사용자 `403`이며, 상태 변경 메서드는 유효한 CSRF 토큰이 있어도 허용되지 않습니다. JMX로도 노출하지 않습니다.

Swagger UI는 게시판 API를 제공하며, 관리용 상태 조회는 위 URL에서 직접 확인합니다. 실행과 접근 제한은 [README의 Actuator 상태 확인](../README.md#actuator-상태-확인)을 참고합니다.

## 공통 규칙

- JSON 요청·응답은 UTF-8입니다. 파일 업로드는 `multipart/form-data`, 다운로드는 바이너리 응답입니다.
- 인증은 `JSESSIONID` 세션 쿠키로 유지합니다. 세션 유휴 만료 시간은 30분입니다.
- 모든 POST·PUT·DELETE 요청에는 `XSRF-TOKEN` 쿠키와 같은 값의 `X-XSRF-TOKEN` 헤더가 필요합니다.
- 일반 인증은 `GET /api/auth/csrf` → 회원가입 → 로그인 → CSRF 재발급 순서로 시작합니다. Google 로그인은 아래 브라우저 흐름을 사용합니다. 로그인·로그아웃 후에는 토큰을 다시 발급받습니다.
- Swagger UI는 발급된 CSRF 쿠키를 읽어 헤더를 자동 설정합니다. 다른 클라이언트는 쿠키 저장과 헤더 설정을 직접 처리합니다.
- 수정은 `PUT`으로 제목·본문 또는 댓글 내용을 모두 전달합니다. 작성자 ID는 요청 본문에서 받지 않고 로그인 사용자로 결정합니다.
- 생성은 `201`, 조회·수정은 `200`, 삭제·로그아웃은 본문 없는 `204`를 반환합니다.

## 도메인 관계와 권한

| 관계 | 의미 |
| --- | --- |
| 사용자 1 : N 게시글 | 게시글마다 작성자 1명이 존재 |
| 사용자 1 : N 댓글 | 댓글마다 작성자 1명이 존재 |
| 게시글 1 : N 댓글 | 댓글은 하나의 게시글에 속함 |
| 게시글 1 : N 첨부파일 | 파일은 하나의 게시글에 속하며 게시글 작성자가 관리 |
| 사용자 : OAuth 계정 | Google의 `sub`로 게시판 사용자를 식별; 기존 이메일 계정과 자동 연결하지 않음 |

비회원은 게시글·댓글·파일 목록과 게시글 상세·파일 다운로드를 이용할 수 있습니다. 로그인 사용자는 게시글과 댓글을 작성할 수 있습니다. 게시글 수정·삭제와 파일 추가·삭제는 게시글 작성자만, 댓글 수정·삭제는 댓글 작성자만 가능합니다. 게시글 작성자라도 다른 사용자의 댓글을 개별 수정·삭제할 수 없습니다.

게시글을 삭제하면 댓글은 DB 외래키의 `ON DELETE CASCADE`로 함께 삭제하고 파일 메타데이터도 삭제합니다. 실제 파일은 DB 커밋 후 삭제합니다. 파일 하나를 삭제해도 게시글과 댓글은 유지됩니다.

## 인증

| 메서드·경로 | 입력 | 정상 응답 |
| --- | --- | --- |
| `GET /api/auth/csrf` | 없음 | CSRF 토큰 및 쿠키, 200 |
| `GET /api/auth/providers` | 없음 | Google 사용 가능 여부, 200 |
| `POST /api/auth/signup` | 이메일·닉네임·비밀번호 | 사용자 정보, 201 |
| `POST /api/auth/login` | 이메일·비밀번호 | 사용자 정보·로그인 세션, 200 |
| `GET /api/auth/me` | 로그인 세션 | 사용자 정보, 200 |
| `POST /api/auth/logout` | CSRF 토큰 | 현재 세션·쿠키 무효화, 204 |

회원가입은 자동 로그인하지 않습니다. 로그인 시 세션 ID를 교체합니다. 로그아웃은 유효한 CSRF 토큰이 있으면 로그인 세션이 없어도 `204`를 반환합니다.

회원가입 요청:

```json
{"email":"test@example.com","nickname":"tester","password":"password123"}
```

로그인 요청:

```json
{"email":"test@example.com","password":"password123"}
```

회원가입·로그인·내 정보 응답 예시:

```json
{"id":1,"email":"test@example.com","nickname":"tester"}
```

일반 가입의 이메일은 필수·이메일 형식·최대 100자·중복 불가, 닉네임은 공백만 허용하지 않는 2~100자입니다. 비밀번호는 가입 8~72자, 로그인 1~72자이며 영문 대소문자·숫자·ASCII 특수문자만 허용합니다. 허용 범위는 `U+0021`~`U+007E`이며 공백·탭·개행·한글·이모지·전각 문자 등 나머지는 거부합니다. 문자 종류별 필수 혼합 조건은 없습니다. 허용 특수문자 32개는 다음과 같습니다.

```text
!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~
```

서버는 전체 비밀번호에 문자 정책과 기존 UTF-8 72바이트 제한을 적용하므로 직접 API를 호출해도 우회할 수 없습니다. 입력을 trim·치환·자르기하지 않습니다. BCrypt 해시로 저장하며 정상·오류 응답에 원문을 포함하지 않습니다. 기존에 한글·공백 등 금지 문자로 만든 테스트 계정은 새 로그인 규칙에서 거부되며 기존 해시는 수정하지 않습니다.

### Google 로그인

사용 가능 여부 조회는 비회원에게도 `200`을 반환하며 Client ID·Secret을 포함하지 않습니다.

```json
{"google":{"enabled":false,"authorizationUrl":"/oauth2/authorization/google"}}
```

활성화된 경우 브라우저가 `/oauth2/authorization/google?returnTo=...`로 이동합니다. 서버는 Google OIDC Authorization Code 흐름을 시작하고 `/login/oauth2/code/google`에서 응답을 검증합니다. 최초 로그인에 게시판 회원을 생성하고, 기존 Google 계정은 `sub`로 조회합니다. 같은 이메일의 일반 가입 계정이 있으면 계정을 자동 연결하지 않습니다. 성공 시 정규화한 게시판 목록·상세·작성·수정 주소로 이동하며 `JSESSIONID`로 기존 API를 사용합니다. 로그아웃은 게시판 세션만 종료합니다.

Google 이메일은 `email_verified=true`·올바른 이메일 형식·최대 254자를 요구합니다. Google 회원의 게시판 비밀번호는 없으며 일반 이메일·비밀번호 로그인은 `401`로 거부합니다. 닉네임은 제공된 이름의 제어문자·양끝 공백을 정리하고 최대 100자로 제한하며, 이름이 없으면 `Google 사용자`를 사용합니다. 재로그인은 처음 저장한 이메일·닉네임을 유지합니다. 일반 가입의 이메일 100자·비밀번호 규칙은 변경하지 않습니다. `oauth_accounts`에는 provider·subject·user_id 연결만 저장하고 Access Token·Refresh Token을 저장하지 않습니다.

local·docker 실행의 DB 변경은 Flyway로 관리하고 Hibernate는 스키마를 검증합니다. V1은 기본 게시판 스키마, V2는 이메일 컬럼 확장·비밀번호 NULL 허용·OAuth 계정 테이블을 적용합니다. 기존 게시판 DB는 V1 기준 기록 후 V2부터 적용하며, 새 DB는 V1부터 실행합니다.

실패 시 로그인 페이지의 `oauthError`에는 고정된 값만 사용합니다.

| 값 | 화면 안내 |
| --- | --- |
| `cancelled` | Google 로그인 취소; 재시도 또는 일반 로그인 |
| `email_conflict` | 기존 이메일·비밀번호 로그인 필요; 자동 연결 없음 |
| `invalid_identity` | Google 계정 정보를 확인할 수 없음 |
| `failed` | 일반 Google 로그인 실패 |

화면은 오류 원문·임의 쿼리를 그대로 출력하지 않습니다. 자격 증명은 저장소에 포함하지 않으므로 실행 환경에서 별도로 설정합니다.

## 게시글

| 메서드·경로 | 기능 | 권한 |
| --- | --- | --- |
| `GET /api/posts` | 목록·제목/본문 검색 | 공개 |
| `GET /api/posts/{postId}` | 상세 조회 | 공개 |
| `POST /api/posts` | 작성; JSON 또는 파일 동시 첨부 multipart | 로그인 |
| `PUT /api/posts/{postId}` | JSON 제목·본문 수정 또는 multipart 글·첨부 동시 수정 | 게시글 작성자 |
| `DELETE /api/posts/{postId}` | 게시글과 하위 데이터 삭제 | 게시글 작성자 |

기존 JSON 작성·수정 요청(`Content-Type: application/json`):

```json
{"title":"첫 번째 게시글","content":"게시글 본문입니다."}
```

파일과 함께 작성할 때는 같은 `POST /api/posts`에 `multipart/form-data` 한 요청을 보냅니다.

| 파트 | 형식 | 값 |
| --- | --- | --- |
| `post` | `application/json`, 필수 | 위와 동일한 `title`·`content` JSON 객체 |
| `files` | 파일, 선택 | 최대 5개; 여러 파일은 `files` 파트를 반복 |

파일은 각각 10 MiB 이하이며, 제목·본문 JSON과 multipart 부가 데이터를 포함한 전체 요청은 50 MiB 이하입니다. 파일 없이 `post` 파트만 보내도 됩니다. `201` 응답은 생성한 게시글의 `PostResponse`이며 첨부파일 목록은 별도 조회합니다. 첨부 저장이 실패하면 게시글·첨부 메타데이터를 같은 DB 트랜잭션에서 롤백하고 이미 저장된 파일 정리를 시도합니다. 파일시스템과 DB는 하나의 원자적 트랜잭션이 아니므로 강제 종료·정리 실패 시 물리 파일이 남을 수 있습니다.

제목은 1~200자, 본문은 1~10,000자이며 공백만 입력할 수 없습니다. 입력 원문을 저장하고 HTML 태그는 화면에서 실행하지 않습니다. 작성·상세·수정 응답 예시:

```json
{
  "id":1,
  "title":"첫 번째 게시글",
  "content":"게시글 본문입니다.",
  "author":{"id":1,"nickname":"tester"},
  "createdAt":"2026-09-07T08:00:00Z",
  "updatedAt":"2026-09-07T08:00:00Z"
}
```

파일은 multipart 작성 요청으로 함께 첨부하거나, 생성 응답의 `id`를 사용해 파일 API로 나중에 첨부할 수 있습니다. 기존 JSON 작성 API도 유지합니다. 작성자는 수정으로 바뀌지 않으며 생성 시각은 유지되고 수정 시각은 갱신됩니다.

### 글과 첨부파일 동시 수정

수정 화면은 `PUT /api/posts/{postId}`에 `multipart/form-data` 한 요청을 보냅니다. 필수 `post` 파트의 Content-Type은 `application/json`이며 다음 5개 필드를 모두 전달합니다. `files`는 추가할 신규 파일이 있을 때만 같은 이름으로 반복합니다.

```json
{
  "title": "수정한 제목",
  "content": "수정한 내용",
  "updatedAt": "2026-09-08T06:30:00.123456Z",
  "attachmentIds": [11, 12],
  "deletedFileIds": [12]
}
```

| 필드 | 규칙 |
| --- | --- |
| `title`, `content` | 작성과 같은 길이·공백 검증, 입력 원문 저장 |
| `updatedAt` | 처음 조회한 게시글 응답의 문자열을 변환 없이 전달 |
| `attachmentIds` | 처음 조회한 **전체** 첨부파일 ID 목록; 삭제 선택한 ID도 포함 |
| `deletedFileIds` | 저장과 함께 삭제할 ID; `attachmentIds`의 부분집합 |

두 ID 배열은 비어도 되지만 생략·`null`은 허용하지 않습니다. 배열마다 최대 1,000개이며 중복·`null`·0·음수 ID를 거부합니다(`400`). `attachmentIds`는 순서에 상관없이 서버의 현재 전체 ID 집합과 같아야 합니다. 서버의 현재 `updatedAt` 또는 첨부파일 집합이 달라졌으면 변경하지 않고 `409`를 반환합니다. 새 내용을 불러와 확인한 뒤 다시 저장해야 합니다.

신규 파일은 한 요청에 최대 5개, 파일당 10 MiB, JSON·multipart 부가 데이터를 포함한 전체 요청은 50 MiB 이하입니다. 기존 파일과 신규 파일의 총 개수를 5개로 제한하지는 않습니다. 성공 응답은 DB에 저장된 수정 시각을 포함한 `PostResponse`(`200`)이며, 첨부파일 목록은 별도 조회합니다.

글·첨부파일 메타데이터 변경은 같은 DB 트랜잭션에서 처리합니다. 실패하면 변경을 롤백하고 새로 저장한 물리 파일 정리를 시도합니다. 삭제 선택한 기존 물리 파일은 DB 커밋 후에만 삭제합니다. DB와 파일시스템은 완전한 원자성을 보장하지 않으므로 I/O 실패·강제 종료·커밋 결과 불명확 시 파일 정리 작업이 필요할 수 있습니다.

기존 JSON `PUT`의 `{title, content}` 요청과 `200` 응답은 유지합니다. 위 수정 시각·첨부 집합 충돌 확인은 새 multipart 수정 요청에 적용합니다.

## 댓글

| 메서드·경로 | 기능 | 권한 |
| --- | --- | --- |
| `GET /api/posts/{postId}/comments` | 댓글 목록 | 공개 |
| `POST /api/posts/{postId}/comments` | 댓글 작성 | 로그인 |
| `PUT /api/posts/{postId}/comments/{commentId}` | 댓글 수정 | 댓글 작성자 |
| `DELETE /api/posts/{postId}/comments/{commentId}` | 댓글 삭제 | 댓글 작성자 |

작성·수정 요청은 `{"content":"좋은 글 감사합니다."}`입니다. 내용은 1~2,000자이며 공백만 입력할 수 없습니다. 응답 예시:

```json
{
  "id":2,
  "postId":1,
  "content":"좋은 글 감사합니다.",
  "author":{"id":2,"nickname":"reader"},
  "createdAt":"2026-09-07T08:01:00Z",
  "updatedAt":"2026-09-07T08:01:00Z"
}
```

댓글의 `commentId`가 존재하더라도 경로의 `postId`에 속하지 않으면 `404`를 반환합니다. 존재하지 않는 게시글의 댓글 목록도 `404`입니다.

## 페이징과 검색

게시글·댓글 목록은 `page`와 `size`를 사용합니다.

| 파라미터 | 기본값 | 범위·동작 |
| --- | --- | --- |
| `page` | 0 | 0부터 시작, 음수 불가 |
| `size` | 20 | 1~100 |
| `keyword` | 없음 | 게시글 목록 전용, 최대 100자 |

게시글은 작성 시각·ID 내림차순, 댓글은 작성 시각·ID 오름차순으로 정렬합니다. 게시글 검색은 제목 또는 본문에 검색어가 포함된 게시글을 반환하며 대소문자를 구분하지 않습니다. 검색어의 앞뒤 공백은 제거하고 빈 검색어는 전체 조회합니다. `%`·`_`는 일반 문자로 검색합니다.

```text
GET /api/posts?page=0&size=20&keyword=Spring
GET /api/posts/1/comments?page=0&size=20
```

목록 공통 응답은 다음 구조이며 `content`에 해당 게시글 또는 댓글 응답 객체가 들어갑니다. 범위를 벗어난 페이지는 빈 `content`를 반환합니다.

```json
{
  "content":[],
  "page":0,
  "size":20,
  "totalElements":0,
  "totalPages":0,
  "first":true,
  "last":true
}
```

## 첨부파일

| 메서드·경로 | 기능 | 권한 |
| --- | --- | --- |
| `GET /api/posts/{postId}/files` | 파일 목록 | 공개 |
| `POST /api/posts/{postId}/files` | 파일 업로드 | 게시글 작성자 |
| `GET /api/files/{fileId}/download` | 파일 다운로드 | 공개 |
| `DELETE /api/files/{fileId}` | 파일 삭제 | 게시글 작성자 |

업로드는 `multipart/form-data` 요청이며 필드 이름은 `files`입니다. 같은 필드를 반복해 한 요청에 1~5개를 전달합니다. 파일마다 10 MiB(10 × 1,024 × 1,024바이트) 이하, 전체 요청은 50 MiB 이하입니다. 전체 요청 제한에는 multipart 부가 데이터도 포함됩니다.

Swagger UI의 파일 업로드 API에서 `postId`를 입력하고 `files` 항목에 파일을 선택해 전송합니다. 로그인 후 CSRF 토큰을 다시 발급받은 상태여야 합니다.

업로드 응답은 `201`, 목록 응답은 `200`이며 모두 아래와 같은 JSON 배열입니다.

```json
[
  {
    "id":3,
    "originalFilename":"설명서.txt",
    "size":120,
    "contentType":"application/octet-stream",
    "downloadUrl":"/api/files/3/download"
  }
]
```

`size`의 단위는 바이트입니다. 저장용 UUID·서버 디렉터리는 응답하지 않습니다. 다운로드는 `downloadUrl`로 요청하며 `application/octet-stream`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` 헤더와 파일 내용을 반환합니다. 한글 원본 파일명은 다운로드 이름에 반영합니다.

빈 파일은 거부합니다. UNIX·Windows 원본 경로는 제거하고 마지막 파일명만 보관하되, `..` 경로 구성요소·제어문자·공백뿐인 이름·255자를 초과하는 이름은 거부합니다. 예를 들어 `C:\fakepath\설명서.txt`는 `설명서.txt`로 보관하고 `../설명서.txt`는 거부합니다. 실제 파일은 지정된 업로드 디렉터리에 UUID로 저장합니다.

업로드 트랜잭션 실패 시 새 파일을 정리하고, 삭제 시 DB 커밋 후 실제 파일을 삭제합니다. DB와 파일시스템은 원자적 트랜잭션이 아니므로 강제 종료·삭제 실패 시 파일이 남을 수 있습니다. 정리 실패는 서버 로그에 기록되며 저장소 문제를 해결한 뒤 해당 UUID 파일을 수동 정리해야 합니다.

## 웹 화면 구현 현황

`GET /`는 로그인 없이 게시글 목록 HTML을 제공합니다. 검색·페이지 이동·페이지 크기 변경은 `GET /api/posts`에 연결됩니다. 제목을 누르면 `GET /post.html?id=게시글ID`로 이동하여 본문·첨부파일·댓글을 조회합니다. 상세 화면은 로그인 세션이 있으면 댓글 작성·본인 댓글 수정·삭제와 본인 게시글의 수정 화면 연결·삭제를 지원합니다. 상태 변경 시 CSRF 토큰을 다시 조회하고, 실패한 요청을 자동 재시도하지 않습니다.

`GET /write.html`은 제목·본문 입력, 파일 선택·제거와 등록을 제공합니다. 비회원도 초안과 파일을 준비할 수 있으며 등록에는 로그인이 필요합니다. 로그인·회원가입은 새 탭에서 열고, 원래 탭으로 돌아오거나 상태 확인 버튼을 누르면 입력 내용과 파일 선택을 유지한 채 세션을 갱신합니다. 등록 직전 세션을 확인하고 `post` JSON과 선택한 `files`를 multipart 한 요청으로 보냅니다. 성공하면 생성된 글의 상세 화면으로 이동하며, 목록의 `keyword`·`page`·`size` 조건을 보존합니다. 취소는 같은 조건의 목록으로 돌아갑니다.

작성 초안과 선택한 파일은 현재 탭에서만 유지하며 새로고침·탭 닫기는 보존하지 않습니다. 입력이 있을 때 이탈을 확인합니다. 결과가 불확실한 등록 요청은 자동 재시도하지 않고 재등록을 막습니다. 새 탭의 목록에서 등록 여부를 확인한 뒤, 등록되지 않았음을 확인한 사용자가 다시 작성할 수 있습니다.

`GET /edit.html?id=게시글ID`는 작성자만 기존 제목·본문과 첨부파일을 변경할 수 있는 화면입니다. 삭제 선택은 저장 전까지 서버에 반영하지 않습니다. multipart 수정의 `409`에서는 입력·선택 파일을 보존하고, 사용자가 최신 내용을 다시 불러오면 기존 초안을 교체합니다. 로그인 만료는 새 탭에서 로그인한 후 원래 탭의 초안을 유지하며 복구할 수 있습니다. 저장·취소는 같은 검색·페이지 조건의 상세로 돌아갑니다. 직접 수정 주소의 `preview`는 허용하지 않습니다.

저장 결과가 불확실하면 자동 재전송하지 않고 저장 버튼을 막습니다. 작성자는 현재 입력을 복사·편집할 수 있으며 새 탭에서 저장된 글을 확인한 뒤 최신 내용을 명시적으로 불러옵니다. 조회에 성공한 경우에만 초안·파일 선택을 교체하고, 실패하면 그대로 유지합니다. 현재 탭의 초안은 새로고침·탭 닫기로 사라집니다. 수정하지 않은 제목·본문은 서버에서 받은 원문을 다시 전송하므로 파일만 바꾸어도 기존 줄바꿈이 임의로 변경되지 않습니다.

상세의 수정 링크는 작성자에게만 활성화합니다. 댓글 작성·수정 초안이 있으면 같은 탭에서 이동하기 전 이탈을 확인하고, 취소하면 댓글을 유지합니다. 새 탭으로 링크를 열 때는 원래 탭의 초안을 그대로 유지합니다. 수정 URL은 양의 Long 범위 `id`와 `keyword`·`page`·`size`만 재구성하며, 로그인 복귀에서도 해시·미리보기·기타 파라미터를 제거합니다.

`GET /login.html`은 이메일·비밀번호 입력, 비밀번호 표시 전환, 입력 오류·인증 실패 안내를 제공합니다. 로그인 요청 전 CSRF 토큰을 조회하고 `POST /api/auth/login`을 호출합니다. 성공하면 `returnTo`에 지정한 게시판 목록·상세·작성·수정 주소로 복귀하며 검색·페이지 조건을 보존합니다. 외부 URL·API 경로·로그인 페이지 등 허용되지 않은 복귀 주소는 `/`로 대체합니다. 비밀번호는 URL·웹 저장소에 기록하지 않으며 성공·화면 이탈 시 입력창에서 제거합니다. 기존 세션이 있으면 닉네임·돌아가기·로그아웃 후 계정 전환을 제공합니다.

로그인 화면은 Google 버튼과 이메일 폼을 함께 제공합니다. `/api/auth/providers`가 활성화 상태와 고정된 내부 시작 주소를 반환할 때만 Google 이동을 허용하며, 조회 실패·비활성화 시에도 일반 폼은 동작합니다. 연결 상태를 재확인할 수 있고 Google 이동 시 비밀번호 입력을 비우며 폼 로그인·계정 전환과의 중복 동작을 차단합니다. 뒤로 가기 복원 시 세션·연결 상태를 다시 조회합니다. 별도의 Google 회원가입 페이지는 사용하지 않습니다.

`GET /signup.html`은 이메일·닉네임·비밀번호·비밀번호 확인을 입력받습니다. 이메일·닉네임의 앞뒤 공백을 제거하고 길이·이메일 형식·비밀번호 8~72자 및 허용 ASCII 문자·확인 값 일치를 검사합니다. 로그인과 회원가입은 공통 `password-policy.js`를 사용하며 입력란 아래에서 허용 특수문자 전체를 확인할 수 있습니다. 금지 문자가 포함된 붙여넣기·드롭을 취소하고 안내하며, 허용된 입력은 임의로 변환하지 않습니다. CSRF 토큰을 조회한 뒤 `POST /api/auth/signup`에 이메일·닉네임·비밀번호만 전송합니다. 중복 이메일 등 실패를 안내하고 자동 재시도하지 않습니다. 성공하면 비밀번호 입력을 지우고, 기존 게시판 복귀 주소와 `registered=1`만 포함한 로그인 주소로 이동해 가입 완료 안내를 표시합니다. 가입 자체는 로그인하지 않습니다. 비밀번호 두 입력창은 페이지 이탈 시에도 지우며 URL·웹 저장소에 보관하지 않습니다.

목록·상세 상단은 세션에 따라 로그인·회원가입 또는 닉네임·로그아웃을 표시합니다. 상세에서 댓글 초안이나 수정 중인 댓글이 있으면 로그인·회원가입 링크를 새 탭에서 열어 현재 입력을 보존합니다. 원래 탭으로 돌아오거나 `로그인 상태 확인`을 누르면 댓글 DOM을 다시 만들지 않고 인증·작성자 권한을 갱신합니다. 페이지 새로고침·탭 닫기는 초안을 보존하지 않습니다.

`/post.html?preview=1`은 API 요청·DB 저장 없이 예시 콘텐츠로 디자인을 확인하는 읽기 전용 모드입니다. 실제 쓰기·로그인·회원가입·다운로드·수정 화면 이동은 실행하지 않습니다.

## 오류와 검증 현황

오류 응답 예시:

```json
{"message":"게시글을 찾을 수 없습니다."}
```

| 상태 | 발생 조건 |
| --- | --- |
| 400 | 입력 검증·JSON·페이지 오류, 중복 이메일, 빈 파일, 파일 개수·이름 오류 |
| 401 | 로그인 실패 또는 로그인 필수 API에 세션 없음 |
| 403 | CSRF 토큰 누락·불일치, 다른 작성자의 데이터 수정·삭제 |
| 404 | 게시글·댓글·파일 없음, 댓글의 게시글 경로 불일치 |
| 409 | 동시 변경 요청 충돌; multipart 수정 시 오래된 수정 시각·첨부파일 집합, 최신 내용 확인 필요 |
| 413 | 파일당 10 MiB 또는 전체 multipart 요청 50 MiB 초과 |
| 500 | 파일 저장소 등 서버 내부 처리 오류 |

CSRF 검증은 로그인 판정보다 먼저 실행됩니다. 상태 변경 요청에 세션과 CSRF 토큰이 모두 없다면 `401` 대신 `403`이 먼저 반환될 수 있습니다.

전체 Java 테스트 **326개**와 JavaScript 검증 **209개**를 통과했습니다. 인증·작성자 권한·CSRF, 입력·비밀번호 정책, 게시글·첨부파일 동시 변경과 충돌·실패 롤백, 초안 보존과 안전한 복귀, 테스트용 OIDC 제공자를 통한 토큰 검증·세션 연결, Actuator 상태·접근 제한을 검증합니다. Docker의 실제 HTTP로 주요 API, 파일 다운로드 바이트, 업로드 용량 제한, 데이터 유지와 Actuator 상태 조회·비공개 경로 차단을 확인했습니다. Java 테스트는 H2, JavaScript 검증은 Node VM과 최소 DOM을 사용하며 실제 브라우저 배치·파일 선택창·BFCache 진입은 자동 검증 범위에 포함하지 않습니다. 실행 명령과 상세 범위는 [README의 빌드 및 테스트](../README.md#빌드-및-테스트)를 참고합니다.
